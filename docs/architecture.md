# Architecture

```
WomierDriver.App (WPF, net10.0-windows)          WomierDriver.Core (net10.0)
┌──────────────────────────────────────┐        ┌──────────────────────────────────────────┐
│ App            single instance, DI   │        │ Automation/DriverEngine   state machine  │
│ Tray/          TaskbarIcon + menu    │ ─────► │   ProcessWatcher          poll processes │
│ ViewModels/    MVVM (Toolkit.Mvvm)   │        │   ProfileSelector         pure decision  │
│ Views/         MainWindow, canvas,   │        │   ReportTravelSource      live travel    │
│                 slider, process pick │        │ Device/Sk75Keyboard       read/write     │
│ Services/      persistence, autorun, │        │   Sk75TmrLayout, ScanCodeMap             │
│                 Raw Input (live view)│        │ Protocol/                 packets, cksum │
└──────────────────────────────────────┘        │ Hid/                      feature + input│
                                                │ Profiles/                 models + JSON  │
                                                └──────────────────────────────────────────┘
```

## Core

* **Protocol** – pure functions: checksum, opcodes, per-key table descriptors, travel unit scale, packet
  builders. No I/O, fully unit tested.
* **Hid** – `IFeatureChannel` (send / exchange one 64-byte feature report) and `IInputReportChannel` (a reader
  thread delivering the keyboard's 32-byte vendor input reports), both implemented on HidSharp, plus
  `KeyboardLocator`, which finds the two vendor collections (usage page `0xFFFF`: usage 2 = configuration,
  usage 1 = input) on VID `0x3151` PID `0x5030` (wired) / `0x5038` (receiver) and exposes hot-plug
  notifications.
* **Device** – `Sk75Keyboard` identifies the board (device id 2518 from `GET_USB_VERSION`), reads the analog
  tables into `KeySettings` per key, writes them back with the vendor's sequence and a read-back check, and
  switches the live travel stream on and off. `Sk75TmrLayout` holds the 81 keys (matrix slot, HID usage,
  legend, geometry) generated by `tools/gen-layout.py`; `ScanCodeMap` maps the PS/2 make codes that Raw Input
  delivers to those keys.
* **Profiles** – `Profile` (name, games, per-slot `KeySettings`, default flag), `ProfileLibrary` (invariants:
  exactly one default), `AppSettings`, atomic JSON persistence in `%APPDATA%\WomierDriver`.
* **Automation** – `ProcessWatcher` samples process names every 2 s; `ProfileSelector` picks manual override →
  first profile whose game is running → default; `ReportTravelSource` decodes the live travel reports into
  per-key samples; `DriverEngine` ties it together.

### DriverEngine state machine

```
          hot-plug / start              process list / profiles / settings / manual choice
                 │                                            │
                 ▼                                            ▼
        Rescan: open interfaces ──► Connected(KeyboardInfo) ──► Evaluate ──► (profile, reason)
                 │ none answer                                                   │ differs from last applied
                 ▼                                                               ▼
           Disconnected ◄──────────── I/O failure ◄──────────────────── Write tables + verify
```

* Everything that touches the device runs under one `SemaphoreSlim`; evaluations are coalesced.
* The library is only mutated through `MutateLibrary`, which takes the engine lock; the engine snapshots the
  keys of the chosen profile under the same lock before writing.
* A manual tray choice stays active until game activity changes (a listed game starts or stops), then
  automatic selection takes over again.
* Writes are skipped when the same profile content (`Profile.KeySignature()`) is already on the keyboard.
  Re-connecting the keyboard resets that memory, so the active profile is re-applied after a replug.

### Live view

* `SetLiveViewAsync(true)` opens the vendor input collection, starts a `ReportTravelSource` and sends `1B 01`;
  every travel report becomes a `LiveTravel` event (slot, raw, mm) raised on the reader thread.
* The stream is switched off before every profile write and on again afterwards, inside the device gate, so
  stream traffic never interleaves with the write sequence. `1B 00` is also sent on every connect (a crashed
  session could have left the stream on) and on dispose.
* When the keyboard disappears the source is dropped synchronously under the gate (no `1B 00`: the device is
  gone); when it comes back while the live view is still requested, `RescanAsync` re-arms it.

## App

* `App` – single instance via a named mutex; a second launch signals a named event that brings the existing
  window to the front. `--minimized` starts in the tray (used by the autostart entry).
* `TrayIconController` – H.NotifyIcon `TaskbarIcon`; the context menu is rebuilt from engine state each time
  it opens: *Automatic (follow games)*, one entry per profile, *Open…*, *Exit*. Left click opens the window.
  Profile switches caused by games raise a toast when enabled.
* `MainViewModel` – profile list, 81 `KeyViewModel`s for the canvas, the `SelectionEditorViewModel` that edits
  all selected keys at once, game rules, settings toggles. Edits are saved (debounced 0.5 s) and pushed to
  the engine (debounced 0.7 s); the engine re-applies only if the edited profile is the active one. The live
  view (`IsLiveViewEnabled`, session-only) collects travel samples in a per-slot array on the reader thread
  and pushes the changed slots to the tiles every 16 ms; it switches itself off when the window hides or the
  keyboard disconnects.
* `RawKeyboardInput` – Win32 Raw Input (`RIDEV_INPUTSINK`) hooked on the main window and filtered to the SK75's
  own keyboard collections; make codes map to key slots through `ScanCodeMap`. Registered only while the live
  view is on and the window is visible. Key events only flip tile state and are never logged or stored. While
  the live view is on the window swallows key presses (except in text boxes and with Alt) so Space and Enter
  do not activate the focused control.
* `KeyboardView` – a `Viewbox`-scaled canvas of key tiles; click, Ctrl/Shift-click and marquee selection. Tiles
  are tinted with the accent colour by actuation depth (shallow = strong) and show a dot when rapid trigger is on.
  In live mode each tile shows a depth bar (a `ScaleTransform` on a rectangle, so no layout pass), a tick at the
  selected profile's actuation point (only when that profile is the active one) and a green outline while Windows
  reports the key as pressed.
* `SettingSlider` – labelled slider + numeric box with a "Mixed" state; drags commit on release.
* Theme: WPF Fluent (`ThemeMode="System"`), so light/dark and accent follow Windows.

## Data

| File | Content |
|---|---|
| `%APPDATA%\WomierDriver\profiles.json` | all profiles |
| `%APPDATA%\WomierDriver\settings.json` | app settings |
| `%APPDATA%\WomierDriver\driver.log` | rolling log (1 MB) |
| `HKCU\…\Run\WomierDriver` | autostart entry (`WomierDriver.exe --minimized`) |

Set `WOMIER_DRIVER_DATA=<folder>` to redirect the data folder (useful for testing). A redirected instance uses
mutex and event names suffixed with a hash of that folder, so it runs side by side with the normal driver.
